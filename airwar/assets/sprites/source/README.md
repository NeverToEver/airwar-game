# Aseprite Source-of-Truth (P2-8)

> **Status:** scaffold. This directory is reserved for artist-editable
> `.ase` source files. The runtime currently still draws ships, bullets,
> and effects procedurally via `airwar/utils/sprites.py`; this scaffold
> exists so that flipping the renderer to load pre-baked PNGs is a
> localized change rather than a new design.

## Why this exists

`airwar/utils/sprites.py` builds every ship, bullet, and glow surface
in code at runtime. The procedural path is fast on first launch
(thousands of `pygame.draw` calls) and the result is cached on disk
via `airwar/utils/generated_asset_cache.py`, so the cost is paid once
per (size, theme) combination. This is fine, but it has three real
costs that Aseprite authorship addresses:

1. **Iteration friction.** A designer who wants a different cockpit
   shape today must edit Python polygon lists, restart the game, and
   eyeball the result. A `.ase` file gives them a proper editor,
   layers, onion-skin, and export presets.
2. **No historical record.** Procedural sprites have no diffable
   history beyond the source code. Artists cannot branch, review, or
   roll back a visual change.
3. **Mixed responsibilities.** Visual design and gameplay logic share
   a single file. Splitting them gives a cleaner ownership boundary.

The motivation in `docs/ROADMAP.md` §5 P2-8 is *"avoid regeneration
and version the assets"* — i.e. bake once, ship the PNGs, no per-run
re-render.

## Path layout

```
airwar/assets/sprites/
├── source/                     # <-- this directory (artist-editable)
│   ├── README.md               # this file
│   └── <artist adds .ase files here, grouped by subdir as needed>
└── (no checked-in PNGs — those live in the platform cache)
```

Recommended subdir convention (not yet populated — create as you
add files):

- `source/ships/` — player, enemy_scout, enemy_elite, boss
- `source/bullets/` — bullet_single, bullet_spread, bullet_laser, missile_explosive
- `source/fx/` — glow_circle, explosion

The bake script picks up `*.ase` recursively under `source/`, so the
subdir layout is purely for human organization; the category prefix
in the output PNG name (`ships_player.png`, `bullets_single.png`,
etc.) is the first path component under `source/`.

The baked PNGs are **not** checked into the repository. They are
regenerated by `scripts/bake_sprites.sh` into the platform-specific
generated-asset cache (see
`airwar/utils/generated_asset_cache.py:generated_asset_cache_dir`).
This keeps the repo small and lets every developer / CI runner build
the same PNGs from the same `.ase` sources.

## When to bake

Bake is **explicit and offline**, never on the hot path. Two windows:

1. **Developer bake (manual).** Run `./scripts/bake_sprites.sh`
   after editing any `.ase` file. The script is idempotent: it
   re-exports only files whose source mtime is newer than the cached
   PNG. Ship the new PNGs alongside the build if you want them
   included in the executable.
2. **CI bake (optional).** A CI job can install the Aseprite CLI,
   run the bake, and upload the cache as a build artifact. The
   game picks it up at startup because
   `load_or_build_generated_surface` looks for the PNG first and
   only re-runs the builder on miss.

There is **no runtime bake**. The game never invokes `aseprite` from
inside the player.

## How baking integrates with the cache

`airwar/utils/generated_asset_cache.py` already provides
`load_or_build_generated_surface(namespace, cache_key, build_surface)`:

- The procedural `build_surface` callback stays the fallback. It is
  invoked only when no PNG is on disk, so contributors without the
  Aseprite CLI can still run the game.
- The bake script writes PNGs into the *same* directory the cache
  reads from, using the same `(namespace, cache_key)` naming. See
  `scripts/bake_sprites.sh` for the filename convention.
- A future `ship_aseprite_surface(ns, key, .ase_path)` function
  would call `aseprite --batch ... --filename <path>` and
  `pygame.image.load()` the result, replacing the procedural
  builder. That change is intentionally out of scope for P2-8; this
  commit only documents the layout and provides the script.

## Backup and release policy

- **Source `.ase` files** are the source of truth and **must** be
  committed. They are small (tens to hundreds of KB) and diffable.
- **Baked PNGs** are **not** committed. For a release build the
  maintainer runs `scripts/bake_sprites.sh --release` and zips the
  output of `generated_asset_cache_dir()` into the release
  artifact. The PyInstaller bundling in
  `build_linux.sh` / `build_macos.sh` / `build_windows.bat` can
  then `--add-data` the zip and the game will load the PNGs
  without re-baking.
- **Tag a release** with the Aseprite version that produced the
  PNGs (e.g. `baked-with-aseprite-1.3.7`). Aseprite's export format
  is stable, but pinning the version avoids silent visual drift
  between releases.

## Open questions (not blocking P2-8)

- Should the game also accept a `--aseprite-source-dir` CLI flag so
  contributors can point at their own checkout?
- Do we need per-cel exports (for animated bullets) or is the
  current "one PNG per cache key" enough?
- How do we surface a "PNG is stale relative to `.ase`" warning
  during development? Probably a mtime-based `DeprecationWarning`
  on first load.

These are tracked in `docs/ROADMAP.md` §5 and will be picked up
under P2-9 or later.
